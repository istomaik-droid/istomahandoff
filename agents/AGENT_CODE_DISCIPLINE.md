# Agent code discipline

Стилевые правила исполнения. Не заменяют полномочия, gates и evidence —
определяют качество работы внутри разрешённого scope. Конвенция уровня E0.

## Предположения и неоднозначность

1. Называть предположения явно до implementation.
2. При неоднозначном запросе — показать трактовки и спросить, не выбирать молча.
3. Если есть решение проще — предложить его до начала работы.
4. При обнаружении противоречия в источниках — назвать его, не разрешать молча.

## Минимализм

1. Нет фич, абстракций и конфигурируемости сверх запрошенного.
2. Нет error handling для невозможных сценариев.
3. Если решение можно сделать заметно короче без потери требований — сократить.
4. Тест: senior engineer не назвал бы это переусложнённым.

## Хирургичность диффа

1. Каждая изменённая строка следует из owner decision / work package.
2. Не «улучшать» соседний код, стиль и форматирование.
3. Не рефакторить то, что не сломано и не входит в scope.
4. Чужой мёртвый код — упомянуть в report, не удалять.
5. Удалять только то, что осиротело из-за собственных правок.

## Проверяемые цели

1. Задачу формулировать как критерий успеха: `шаг → проверка`.
2. Багфикс начинается с теста, воспроизводящего баг (docs/30).
3. «Готово» — только после фактического прохождения проверок,
   с командами и counts (agents/AGENT_PROGRESS.md).

## Источник

Принципы адаптированы из наблюдений Andrej Karpathy о типичных ошибках
LLM при кодировании (репозиторий forrestchang/andrej-karpathy-skills, MIT).

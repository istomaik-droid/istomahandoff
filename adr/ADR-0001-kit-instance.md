# ADR-0001: Разделение кита и экземпляра — «два корня»

Status: accepted

Date: 2026-10-17

Deciders: OWNER

Owner decision: DEC-0018

## Context

Сервер, lint и тесты знают один корень `ROOT`: он одновременно канон (нормы,
схемы, шаблоны, код) и экземпляр (журнал решений, active state, memo,
evidence, git-дерево конкретного проекта). Обзор экземпляров 17.10 показал
последствия:

- Экземпляры получают канон копированием каталогов кита. Копии застывают на
  старой версии, исправления кита (например, DEC-0016/0017) до них не
  доходят; проектные проверки правят код кита в копии.
- Вместе с `docs/10` в журналы проектов попадают записи журнала протокола —
  как собственные полномочия проекта; одни и те же номера DEC в проекте и в
  ките означают разные решения.
- Файлы протокола экземпляра могут оказаться вне git — только в рабочей
  копии.
- Решение проекта уже попадало в журнал протокола: пользовательский конфиг
  рантайма направлял все проекты в клон протокола.
- Схемы установки разнятся; режим `ISTOMAHANDOFF_ROOT=<проект>` на практике
  не используется.

Инструменты почти без пересечений делятся на «только канон» и «только
проект»; оба корня нужны лишь `record_decision` (enum типов — из схемы
канона, запись — в журнал проекта).

## Decision

**1. Один установленный кит.** На машине — отдельный чистый клон протокола
(установленный кит). Он меняется только `git pull --ff-only` слитого master
с зелёным CI и запускает сервер из своего `.venv` (`mcp_server/requirements.txt`).
В проекты канон не копируется. Рабочий клон, где развивается протокол, —
обычный проект для этого кита.

**2. Два корня в сервере.**
- CANON — каталог кита, определяется по пути `server.py`; только чтение.
- PROJECT — абсолютный путь из `ISTOMAHANDOFF_PROJECT`. Это единственный
  ключ записи; он появляется в конфиге проекта по решению владельца о
  подключении проекта. `CLAUDE_PROJECT_DIR` используется только для чтения и
  сверки: если оба заданы и указывают в разные каталоги — отказ.
- `ISTOMAHANDOFF_ROOT` устаревает: с ней сервер не стартует и подсказывает
  `ISTOMAHANDOFF_PROJECT`.

**3. Fail-closed.** Tools экземпляра (`record_decision`, `checkpoint_create`,
`pre_deploy_check`, `get_active_state`, `list_expired`, `audit_sample`,
`evidence_hash`) без PROJECT или без `PROJECT/docs/10_DECISION_LOG.md`
отказывают с подсказкой `instance_init`. Канон — resources, prompts,
`validate_transition`, `protocol_version`, `read_canon`, lint кита — доступен
всегда.

**4. Нет записи туда, где лежит канон.** `record_decision` и
`checkpoint_create` отказывают, если PROJECT совпадает с китом или лежит
внутри него (после `resolve()`), либо если в корне PROJECT лежит канон
(`istomahandoff.md` и `docs/16_STATE_MACHINE.md`) — то есть это клон
протокола или проект с копией кита. Журнал протокола до назначения
единственного писателя ведётся вручную через pull request (DEC-0016).

**5. Ревизия кита.** Сервер запоминает HEAD кита при старте. Запись
отказывает, если у отслеживаемых файлов кита есть незакоммиченные изменения
или HEAD кита сменился после старта (нужен перезапуск); `.venv` и кэши
кита — в `.gitignore`. `protocol_version` отдаёт ревизию
загруженного кода, ревизию на диске и релизный тег.

**6. HTTP-режим.** Tools записи в HTTP-режиме отказывают, пока у сервера нет
аутентификации.

**7. Файлы экземпляра — на прежних путях проекта.** `docs/09_ACTIVE_STATE.md`,
`docs/10_DECISION_LOG.md` (собственный блок «## Записи»),
`docs/11_HANDOFF_MEMO.md`, `evidence/`, `templates/PROJECT_PROFILE.yaml`.
Схема журнала, enum типов, state machine, версии — только из кита: копия
схемы в журнале проекта не читается.

**8. Записи журнала протокола наружу не отдаются.** Ресурс `docs/10` и
`read_canon` отдают схему и правила с пустым блоком «## Записи»; enum типов
берётся строго из схемы кита (до «## Записи»).

**9. Инструменты.**
- `tools/instance_init.py <проект>` — создаёт файлы экземпляра из шаблонов
  кита без записей протокола и правило `evidence/** -text` в `.gitattributes`;
  существующие файлы не перезаписывает.
- `protocol_lint.py --project <путь>` — журнал проекта по инвариантам и схеме
  кита; `docs/09` — версия из `docs/42`, состояние из `docs/16` кита.
  Предупреждения: в проекте лежит копия кита; нет правила `.gitattributes`;
  в журнале есть записи, побайтно равные записям журнала протокола (импорт).
- Tool `read_canon(path)` — чтение канона по белому списку (для рантаймов,
  которые не показывают модели resources).

**10. Версии.** Annotated-теги `kit-vX.Y` на каждую новую строку `docs/42`;
ретро-теги — там, где коммит версии однозначен. Minor мигрирует
автоматически по docs/47 п.5: docs/34 п.12 и правило docs/09 выравниваются
под него (агент обновляет `protocol.version` и пишет событие в `docs/11`).
Major — только решение MIGRATION владельца; старая версия для in-flight
work item закрепляется отдельным worktree кита на нужном теге.

**11. Подключение рантаймов.**
- Kimi Code: проектный `.kimi-code/mcp.json` — сервер кита и
  `env.ISTOMAHANDOFF_PROJECT`; пользовательский конфиг — только чтение
  канона (`enabledTools`).
- Claude Code: проектный `.mcp.json` с тем же `env`; в user scope — только
  чтение.
- Codex: `mcp_servers` в `config.toml` с тем же `env`.

**12. Поставки (каждая — отдельное решение владельца).**
- П0 «страховка» — выполнена 17.10: бэкап экземпляров (побайтные копии с
  sha256-манифестом и git bundle) вне проектов; запись в старых копиях
  сервера закрыта `disabledTools` в конфигах проектов; архив старого
  дистрибутива вынесен из каталога кита.
- П1 — код кита по этому ADR (сервер, lint, `instance_init`, тесты,
  документы) — решение в журнале протокола, pull request.
- П2 — установка кита на машине: `.venv`, пользовательский конфиг рантайма,
  пользовательские копии скиллов, перезапуск сессий.
- П3, П4… — миграция экземпляров по одному, каждая — решениями в журнале
  самого экземпляра: подключение к киту; CORRECTION об импорте записей
  протокола (история не правится, номера не меняются); файлы экземпляра — под
  git; удаление копии кита — только файлов, побайтно равных версии кита
  (изменённые решает владелец; посторонние файлы в каталогах кита не
  трогаются). Экземпляры с работой в полёте — после её завершения.
  Экземпляр с собственным форматом журнала не подключается; заброшенный —
  замораживается.

## Consequences

- Исправления кита доходят до всех проектов одним `pull`; копий сервера в
  проектах нет.
- Записи протокола не раздаются проектам; запись решения не уходит в чужой
  журнал: явный ключ, fail-closed и запрет записи туда, где лежит канон.
- Единая точка отказа: неудачное обновление кита ломает все проекты сразу.
  Поэтому обновляется только слитый master с зелёным CI; откат — checkout
  предыдущего тега.
- Канон лежит вне рабочего каталога проекта: модель читает его через
  resources или `read_canon`; право читать кит фиксируется в решении о
  подключении проекта (agents/AGENT_CONTRACT: чтение вне workspace — только по
  решению).
- Работающий сервер держит код до перезапуска — запись при сменённой
  ревизии кита отказывает (п. 5).
- Рантайм, который не сообщает серверу проект, опирается на явный env в
  конфиге проекта; ошибочный путь в нём сервер ловит только в случаях п. 4 —
  поле `project` в ответах агент сверяет со своим корнем.

## Alternatives

- **Вендоринг кита с замком версии в каждом проекте** — отклонён: копии
  сервера остаются в каждом проекте, обновление — N ручных операций, проектные
  проверки правят код кита.
- **Отдельный каталог экземпляра (`.istomahandoff/`)** — отклонён: та же
  польза ценой переезда журналов полномочий (экземпляров и протокола) и
  правки пути журнала в главном правиле.

## Non-claims

- Не защищает от adversarial-агента: фактический enforcement — E0 плюс CI.
- Не проверено в рантайме: перекрывает ли проектный конфиг Kimi
  пользовательский по имени сервера; передаёт ли Claude Code
  `CLAUDE_PROJECT_DIR` stdio-серверу. Проверяется в П2 до миграции
  экземпляров.
- Инстанс на VPS не затрагивается; HTTP-аутентификация не делается.
- Журналы собственного (не YAML) формата не поддерживаются.
